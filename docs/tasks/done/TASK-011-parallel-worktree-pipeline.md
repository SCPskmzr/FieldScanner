# TASK-011 — Пайплайн параллельной работы агентов через git worktree

> **Superseded.** Задача не реализовывалась и разделена на TASK-018
> (корректность гейта покрытия документации), TASK-019 (собственно
> worktree-пайплайн) и TASK-020 (смоук-тест старта приложения). Текст ниже

## Goal

Два агента (например Claude Code и Codex) могут одновременно вести разные
задачи в этом репозитории без порчи рабочего дерева, коммитов и Gradle-стейта.
Гейт завершения задачи — `scripts/verify` (без устройства); установка и запуск
на устройстве вынесены из автоматического пайплайна и запускаются владельцем
репозитория вручную.

## Context

Сейчас весь процесс рассчитан на один рабочий каталог и одного активного
агента:

- `docs/AI_DEVELOPMENT_WORKFLOW.md` прямо запрещает многоагентную работу
  («Do not automate multi-agent orchestration yet»).
- `scripts/verify-and-install.ps1` пишет общие
  `app/build/verify-and-install-status.txt` и `.log`, ставит один и тот же
  пакет `com.fieldscanner.app` на одно устройство и запускает его.
- `scripts/check-documentation.ps1` мапит несколько исходных каталогов
  (`Display/`, `runes/`, `res/layout/`, `MainActivity.kt`) на один
  `docs/modules/ui-and-input.md`, поэтому почти любые две UI-задачи конфликтуют
  в одном файле при слиянии.
- Общий рабочий tree и индекс приводят к тому, что `git commit` одного агента
  захватывает незакоммиченные файлы другого; фичер-ветки этого не решают,
  потому что checkout, `HEAD` и индекс в каталоге одни на всех.

Разделённый рабочий каталог на агента (git worktree) устраняет гонку по
файлам и индексу, оставляя общий `.git`. `scripts/verify` (lint + unit +
assemble + doc-coverage) вычисляет `app/build/` и `.gradle-user-home/` от пути
скрипта, поэтому в отдельном worktree уже изолирован и параллельно-безопасен.

Решение по устройству: установка/запуск на Galaxy XCover 4s **убраны из цикла
задачи**. Их запускает владелец репозитория по своему запросу — обычно на
слитом результате (`main` после мержа задач), а не в каждом worktree. Это
снимает единственный монопольный ресурс из параллельного пути и убирает
необходимость в мьютексе и в суффиксе `applicationId`. Плата — runtime-креши
на старте и проблемы merge манифеста/ресурсов ловятся при ручной установке, а
не автоматически (см. `## Risks`).

## Requirements

- Добавить `scripts/new-worktree.ps1 <TASK-ID>`:
  - создаёт каталог worktree на новой ветке `task-nnn`, ответвлённой от
    актуальной интеграционной ветки репозитория (см. риск про `master`/`main`
    ниже — сначала зафиксировать, какая из них базовая), падает если ветка
    или каталог уже есть;
  - располагает worktree по короткому пути (не sibling глубокого основного
    каталога) и включает `git config core.longpaths true` для него, чтобы не
    упираться в Windows MAX_PATH;
  - выставляет `git config gc.auto 0` на время параллельной сессии, чтобы
    авто-gc в одном worktree не ронял ref-операции в другом;
  - копирует в новый worktree не версионируемые, но нужные для сборки файлы
    (`local.properties`, при наличии — `app/google-services.json` и другие
    локальные секреты), не копируя `.gradle-user-home/` и `build/`;
  - печатает следующий шаг (cd в каталог) без лишнего вывода.
- Добавить `scripts/remove-worktree.ps1 <TASK-ID>`:
  - `git worktree remove` для соответствующего каталога и удаление ветки,
    только если она уже слита в базовую ветку; иначе — понятная ошибка и
    отказ;
  - корректный путь отката на Windows, когда каталог держат хендлы
    (antivirus/Studio/остаточные `*.lock` в `.gradle-user-home`): понятное
    сообщение, опциональный `--force`, без «полу-удалённого» состояния.
- Добавить `scripts/next-task-id.ps1`: сканирует `docs/tasks/` и
  `docs/tasks/done/`, печатает следующий свободный `TASK-NNN` в
  нормализованном формате (три цифры), чтобы два агента не заняли один id.
- Гейт завершения задачи в worktree — `scripts/verify` (без устройства).
  Установка/запуск на устройстве остаётся отдельным ручным шагом владельца
  репозитория; `scripts/verify-and-install.ps1` не входит в per-task
  верификацию и не запускается двумя агентами параллельно.
- Прогонять `scripts/verify` ещё раз на **слитом** результате перед следующим
  merge (интеграционная проверка), чтобы поймать конфликты манифеста/ресурсов
  и общих констант между независимо зелёными ветками.
- Добавить лёгкий параллельно-безопасный smoke-тест старта приложения
  (Robolectric: создание `Application` + инфляция `MainActivity` без падения),
  включённый в `:app:testDebugUnitTest`, — как автоматическая замена части
  сигнала от ручной установки.
- Убрать конфликтную точку в doc-coverage: разнести
  `docs/modules/ui-and-input.md` на устойчивые под-страницы (как минимум
  левый дисплей, нижний статус, руны/ввод) ИЛИ, если полное разбиение вне
  бюджета, задокументировать в файле стабильную структуру `##`-секций.
  Синхронно обновить `coverage`-таблицу в `scripts/check-documentation.ps1`
  (матч по префиксу — проверить, что ни один исходный каталог не остался без
  страницы). Все существующие ссылки на страницу должны продолжать работать.
- Усилить локальный doc-coverage для worktree-режима: `check-documentation.ps1`
  без `-BaseRef` смотрит только незакоммиченные изменения и после коммита в
  worktree проходит вхолостую. Сделать так, чтобы `scripts/verify` в worktree
  сравнивал с точкой ответвления от базовой ветки (`git merge-base`), а не
  только с `HEAD`.
- Переписать раздел «Parallel work» в `docs/AI_DEVELOPMENT_WORKFLOW.md`:
  worktree-процедура, правило «одна ветка — один worktree», выдача id через
  `scripts/next-task-id.ps1`, строго последовательная интеграция в базовую
  ветку через отдельные PR, `scripts/verify` как гейт, ручная установка на
  устройство как отдельный шаг владельца, повторный `verify` на слитом
  результате.
- Обновить «Definition of done» в `AGENTS.md` и чекбокс Verification в
  `docs/tasks/TEMPLATE.md`: развести «task gate» (`scripts/verify`) и
  «integration gate» (ручная установка/запуск на устройстве владельцем).
- Добавить правило в `AGENTS.md` (раздел «Before starting work» или
  «Development rules»): задачи, которые могут идти параллельно, ведутся в
  отдельном worktree через `scripts/new-worktree.ps1`; не запускать двух
  агентов в основном каталоге. Добавить в `scripts/verify.ps1` мягкое
  предупреждение при запуске на базовой ветке.
- Записать в `docs/agent-memory/workflows.md` процедуру worktree, факт, что
  `scripts/verify` параллельно-безопасен, а on-device — ручной шаг владельца,
  и перечень принятых компромиссов из `## Risks`. Обновить `INDEX.md`, если
  появится новый топик.
- Не менять поведение основного каталога при работе без worktree: команды
  `./scripts/verify` и `./scripts/verify-and-install.ps1` без новых
  параметров работают как раньше.

## Risks

Риски сгруппированы; в скобках — предлагаемая мера. Часть закрывается в этой
задаче, часть — принятый компромисс.

### Интеграция / момент слияния

- **Поломка на merge без автоматического сигнала.** Две ветки, каждая зелёная
  по `scripts/verify`, при слиянии дают битый APK: конфликт merge манифеста,
  коллизия ресурсов (дублирующиеся id/строки), рассинхрон общих констант,
  граф `AppContainer`/DI. `verify` на ветке другую ветку не видит; on-device
  гейта в цикле больше нет. Узнаётся при ручной установке, возможно через
  несколько merge'ей, с трудной атрибуцией. (Повторный `scripts/verify` на
  слитом результате + Robolectric smoke-тест старта; on-device перед вливанием
  в базовую ветку.)
- **Runtime-креши на старте не ловятся `assembleDebug`/lint/unit.**
  `Application.onCreate`/DI, битый `FileProvider`, отсутствующий в рантайме
  ресурс, неверная активность. (Robolectric smoke-тест закрывает часть;
  остальное — принятый компромисс, ловится ручной установкой владельца.)

### Слой документации

- **`docs/modules/ui-and-input.md` — гарантированный конфликт.** TASK-006..010
  все мапятся на него через `check-documentation.ps1`. Дробление файла при
  живых 006–010 конфликтует с той задачей, что сольётся позже; без дробления
  каждая параллельная UI-задача всё равно конфликтует в нём, а при разрешении
  конфликта в доке легко потерять кусок. (Сделать TASK-011 до продолжения
  006–010, либо только зафиксировать секции без дробления.)
- **`coverage`-таблица матчит по префиксу.** При дроблении легко оставить
  исходный каталог без страницы — проверка молча промолчит. (Явный тест
  полноты покрытия исходных каталогов.)
- **Doc-coverage гейт вхолостую в worktree.** `check-documentation.ps1` без
  `-BaseRef` = `git diff HEAD` + untracked; после коммита в worktree проходит
  пустым. Частые коммиты в параллельной работе → `docs/modules/` и
  `docs/agent-memory/` тихо расходятся с кодом. (Сравнение с `git merge-base`
  базовой ветки в `scripts/verify` для worktree.)

### Среда Windows

- **MAX_PATH.** `FieldScanner-TASK-NNN\.gradle-user-home\caches\modules-2\
  files-2.1\...` пробивает 260 символов → сборка падает как будто кеш побит.
  Бьёт именно `scripts/verify`, который гоняется чаще всего. (Короткий корень
  worktree + `core.longpaths true` в `new-worktree.ps1`.)
- **Холодный Gradle-кеш × N worktree.** Каждый worktree заново качает
  дистрибутив и зависимости (~1–2 ГБ, минуты); несколько worktree = мульти-ГБ
  дубля, забитый диск проявляется странными ошибками сборки. (Спайк: общий
  `GRADLE_USER_HOME` по фикс-пути с `--no-daemon` vs per-worktree; прежний
  access-denied мог быть про права на профиль, а не про конкурентность.)
- **Ресурсная гонка.** Два Gradle + два Kotlin-демона + два lint на слабой
  станции → своп/OOM, недетерминированные падения. Это практический потолок на
  число параллельных агентов; governor'а нет. (Ограничить двумя агентами;
  задокументировать в workflows.)
- **`git worktree remove` на Windows** падает на залоченных хендлах. (Путь
  отката в `remove-worktree.ps1`.)

### Координация

- **Аллокация id.** Индекс задач убран по дизайну; без механизма два агента
  берут один `TASK-NNN`, обе ветки мержатся → коллизия, ломается связь
  задача↔коммит. `TASK-12` vs `TASK-012` → две ветки на задачу.
  (`scripts/next-task-id.ps1` + нормализация формата.)
- **`master` vs `main`.** Текущая ветка `master`, доки говорят `main`.
  Проверки «слито ли в base» и «worktree от base» будут мимо. (Зафиксировать
  базовую ветку до написания скриптов — блокирующий предшаг.)
- **Ничто не заставляет использовать worktree.** Агент, стартовавший в
  основном каталоге по привычке, возвращает все коллизии рабочего дерева.
  (Предупреждение в `verify.ps1` на базовой ветке; правило в `AGENTS.md`.)
- **Стейл `local.properties`/секретов в worktree.** Копируются один раз при
  создании; изменились в base — worktree молча держит старое. (Отметить в
  workflows; пере-создавать worktree при смене SDK/ключей.)
- **Общий `.git` и авто-gc.** `gc.auto` в одном worktree берёт глобальный лок
  на `packed-refs` и транзиентно роняет ref-операцию в другом. (`gc.auto 0`
  в `new-worktree.ps1`.)

### Принятые компромиссы (не закрываются задачей)

- On-device верификация перестаёт быть автоматической и частью завершения
  задачи; ответственность за неё — на владельце репозитория.
- Runtime-регрессии, не покрытые smoke-тестом, обнаруживаются на интеграции,
  а не на конкретной задаче.
- Параллельность ограничена ресурсами одной рабочей станции.

## Outcome

Задача закрыта как **superseded**, кода по ней не написано. Она была разделена
на три независимо поставляемые задачи:

- **TASK-018** — корректность гейта покрытия документации
  (`docs/tasks/TASK-018-doc-coverage-gate-correctness.md`).
- **TASK-019** — worktree-пайплайн, гейты и документация
  (`docs/tasks/TASK-019-parallel-worktree-pipeline.md`).
- **TASK-020** — смоук-тест старта приложения
  (`docs/tasks/TASK-020-app-startup-smoke-test.md`).

Исправления к тексту выше, перенесённые в задачи-преемники:

- `git config` из linked worktree пишет в общий `.git/config`; «`gc.auto 0` и
  `core.longpaths true` для этого worktree» недостижимо без
  `extensions.worktreeConfig` + `git config --worktree`.
- `core.longpaths` не решает MAX_PATH при сборке — он влияет только на git;
  единственная действующая мера — короткий корень worktree.
- Параллельно-безопасен по кешам только `scripts/verify.ps1`; POSIX-
  `scripts/verify` использует общий `${GRADLE_USER_HOME:-$HOME/.gradle}`.
- `check-documentation` уже использует семантику `merge-base` через
  `"${BaseRef}...HEAD"`; недостающее — объединение с незакоммиченными и
  untracked-файлами, иначе режим базовой ветки ослабляет проверку.
- Правило покрытия для левого дисплея мертво (`.../Display` против реального
  `display/`, сравнение регистрозависимо), плюс вне покрытия `voice/`,
  `journal/`, `audio/`, `camera/`, `data/net/`, `data/location/`, каталоги
  `res/` и часть корневых файлов. Без этого пункт Verification про левый
  дисплей был невыполним.
- В репозитории нет remote и нет ветки `main` — интеграция только локальным
  merge, формулировка «через отдельные PR» неприменима.
- `next-task-id` обязан смотреть все worktree и untracked-файлы (сейчас
  TASK-016/017 не в индексе) и не может быть атомарным.
