- **App language is voice-switched, closed set of 6 (TASK-015).** `voice.AppLanguage` is exactly `ru, pl, be, en, uk, he` (default `ru`); `voice.LanguagePreference` (impl `voice/remote/SharedPrefsLanguagePreference`, prefs file `field_scanner_prefs`, key `app_language`) is the single source, read at point of use by analyzer prompt (`{{OUTPUT_LANGUAGE}}` placeholder), `OpenAiTtsProxy` voice instructions, `VoiceSearchController` recogniser locale and `ScannerViewModel.localeProvider`. No screen menu (child, no visible text) and — after user iteration — **no speech recognition in the switch**: long-press `ASTRA` in `JOURNAL` → `RuneAction.StartLanguageChange` → distinct `RuneContext.LANGUAGE_CHANGE` mode driven by `LanguageChangeController`. It is a spoken carousel by keys: on entry it speaks the *current* language endonym and sits on it; `ASTRA` = `CycleLanguageChange` (next language, spoken), `EMBER` = `ConfirmLanguageChange` (persist + speak once), `DRIFT` = `CancelLanguageChange`. 25 s watchdog re-armed per action; controller depends only on `LanguagePreference` + `LanguageVoice`. `AndroidLanguageVoice` voices endonyms via the cloud `SpeechSynthesizer` (`OpenAiTtsProxy`), not on-device `TextToSpeech` — the device usually lacks `pl/be/uk/he` voices — and caches each clip on disk (`cacheDir/language-voice/endonym-<code>.mp3`); `start()` calls `voice.prewarm(all)`. Cache miss with no network/key → `ToneGenerator` tone. `LanguageCommandMatcher`/`VoiceTextNormalizer`/`Levenshtein`/`ConfirmationMatcher` and the recogniser warm-up/rollback were removed as part of this simplification; `SpeechRecognitionSession` now serves only the journal voice search. No left-zone language indicator. Saved findings keep their original text and audio language. Evidence: `docs/tasks/done/TASK-015-voice-language-switching.md`; `app/src/main/java/com/fieldscanner/app/voice/`; tests `LanguageChangeControllerTest`, `AppLanguageTest`, `RuneBindingsTest`.
- **Layering standard (TASK-012).** Persistence and external services are reached only through an interface port; concrete impls live in a `remote/`-style subpackage and are not imported by UI/`View`/`ViewModel`. Room types stay inside `data/finding`. `View`/`Activity` do no network/file I/O and own no executors — that work sits behind a port assembled in `AppContainer`. New HTTP goes through `com.fieldscanner.app.data.net.HttpClient`, not a hand-rolled `HttpURLConnection`. Sample ports: `FindingStore`, `ImageAnalyzer`, `SpeechSynthesizer` and the left-display pair `OutdoorTemperatureProvider` / `DeviceIndicatorProvider` (`app/src/main/java/com/fieldscanner/app/display/LeftDisplayInputs.kt`). Cross-cutting platform code (geolocation) lives in `com.fieldscanner.app.data.location`, not `data/finding`. Evidence: `AGENTS.md` "Layering standard"; `docs/tasks/done/TASK-012-layering-consistency.md`.

- **"No visible text for children" is fully enforced on live paths (TASK-029).** No residual release-text violations remain. The analysis-result delete `AlertDialog` is gone: deletion of an analysis result now uses the same textless mechanism as the journal — state `ScannerUiState.AnalysisResultDeleteConfirmation(finding)`, bottom-status `BottomStatusMode.DELETE_CONFIRMATION` (trash glyph), and shared runes `RuneAction.ConfirmFindingDeletion` (EMBER) / `CancelFindingDeletion` (DRIFT) in `RuneContext.ANALYSIS_RESULT_DELETE_CONFIRMATION`; cancel returns to `AnalysisResult` with the same finding. All error `Toast`s and the `statusText` `TextView` are removed (`MainScreenView` no longer binds it; `activity_main.xml` has zero `android:text`). Analysis failure, photo-save failure, deletion failure, camera not-ready, camera unavailable / permission denied, and telephony failures now call `DisplayZonesView.playErrorSignal()` — one shared textless ≈0.9 s red pulse over the lower zone (`drawErrorPulse`) — with the specific reason written to the owner `DiagnosticsLog` (`ScannerScreenCoordinator` gained a `DiagnosticsLog` param; `MainActivity.showPhoneError` logs + pulses). `strings.xml` is reduced to `app_name` + the `captured_photo` accessibility description. Regression guard: `app/src/test/java/com/fieldscanner/app/ReleaseTextBarrierTest.kt` fails on any `android:text` under `res/layout/`, or any `Toast`/`AlertDialog` reference in `app/src/main/**.kt` in a file that does not also mention `BuildConfig.DEBUG`. - **The scanner screen is rendered from state; one-shot things go through effects (TASK-028).** `ScannerViewModel.state` has exactly one collector (in `MainActivity.buildScreen()`, next to the `effects` and `CallCoordinator.state` collectors). It maps the state through the pure, Android-free function `scannerScreenModel(state): ScannerScreenModel` (`app/src/main/java/com/fieldscanner/app/ScannerScreenModel.kt`, unit-tested per subtype in `ScannerScreenModelTest`) and hands it to `ScannerScreenCoordinator.render(model)`, which diffs against the previously rendered model and applies only what changed — so re-rendering the same state plays no audio, shows no pulse and restarts no animation. Everything that decides the picture now lives in `ScannerUiState`: `PhotoReview`/`Analyzing` carry `photo: File` (the old `capturedPhotoFile` coordinator field is gone), `Journal`/`JournalDeleteConfirmation` carry `finding: Finding?` (journal move/filter re-emit `Journal`). One-shot cues stay in `ScannerEffect` / rune handlers: analysis-result audio (replay reads `finding.audioUri`; the `analysisAudio` field is gone), shutter flash, the red error pulse, and permission prompts beyond the camera preview. `ScannerEffect.FindingDeleted` was removed (the re-emitted state renders the deletion). `refreshRuneHints()` is called from `render` on a rune-context change and manually **only** where the context source is external to scanner state: language-change entry/exit (`startLanguageChange`, `languageChange.onFinished`) and contacts open/close (`RuneActionRouter`). Deliberately still a coordinator field, not screen state: `audioPermissionTarget` (a pending mic-permission continuation). Process-death restoration (`SavedStateHandle`) is still out of scope — `MainActivity.initialize()` keeps forcing `CameraInactive` on every `onCreate` — but the render path is now the foundation for it. Evidence: `app/src/main/java/com/fieldscanner/app/{ScannerScreenModel,ScannerViewModel,ScannerScreenCoordinator,MainActivity}.kt`, `app/src/test/java/com/fieldscanner/app/{ScannerScreenModelTest,ScannerViewModelTest}.kt`, `docs/tasks/done/TASK-028-render-screen-from-scanner-state.md`.
